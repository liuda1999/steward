## 一、立即重启

保存成功后，提示条上多一个按钮：

```
已写入 config.yaml，共 3 项。
改动需要重启网关才生效。  [立即重启]
```

点它、确认，网关自己重启，新配置生效。

### 怎么做的：同进程重启，不派生新进程

之前我留过一句话：「网关做不到在进程内重启自己——端口还握在自己手里，新进程会和它抢端口」。这个判断只对了一半：**问题不在「同进程」，而在「派生新进程」**。

现在的做法是把 `serve` 改成一个循环：

```
uvicorn 退出  →  重新读配置  →  再造一次 app  →  再起一次 uvicorn
```

端口在两次服务之间就释放了，不会有两个进程抢 27418。而且：

- **日志还在你原来那个终端里**——派生进程的话日志会跑到没人看的地方；
- **不产生孤儿进程**，不用管子进程回收；
- 改 `.env` 里的 key 也能生效：重启前会清掉 `STEWARD_*` / `BASE_*` / `ADVANCED_*` 这几类被配置覆盖的环境变量——`load_env_file` 的规则是「已存在的环境变量优先」，不清掉的话第一次启动读进内存的旧值会一直压着 `.env`。

实现细节：

| 位置 | 做什么 |
|---|---|
| `POST /console/api/restart` | 置位 `server.RESTART["want"]`，延迟 0.3 秒让 uvicorn 优雅退出 |
| `_serve_loop()` | uvicorn 退出后检查标志，重新读配置再起一次 |
| `_clear_env_overrides()` | 重启前清掉被配置覆盖的环境变量 |

那个 0.3 秒延迟是给响应留出发送时间——否则浏览器只看到一个断连，分不清是「重启了」还是「崩了」。前端则在重启期间轮询 `/console/api/state`，服务一恢复就自动刷新界面。

实测：点一次重启，服务 **1 秒内恢复**，PID 不变（同进程），日志里能看到 `[重启] 重新读取配置…` 后重新打印横幅。

## 二、模型标识：让上游自己告诉你有哪些

**「模型标识」必须填上游服务商认的那个字符串，一个字都不能差。** 网关不解释、不纠正，原样转发——所以填错了只会被上游用一句 400 打发。

以 DeepSeek（`https://api.deepseek.com`，OpenAI 兼容）为例：

| 你要的 | 模型标识 |
|---|---|
| Flash / 常规对话 | `deepseek-chat` |
| Pro / 深度思考 | `deepseek-reasoner` |

**推理版是另一个模型名，不是一个开关。** 这是最容易搞错的地方：`thinking: off/on` 发的是 `chat_template_kwargs.enable_thinking`，那是 llama.cpp / vLLM / Qwen 这类**本地服务**认识的扩展参数，云端 API 根本不认。

- **本地模型**：模型标识填模型名或 GGUF 路径（`qwen3:8b`、`/models/qwen3-30b.gguf`），`thinking` 开关有效；
- **云端模型**：模型标识填服务商给的精确名字，`thinking` 开关**基本无效**——要不要思考，取决于你选了哪个模型名。

**别猜，问上游。** 控制台的「测试连接」会读上游的 `/v1/models`，把**真实存在的模型名列出来，点一下就填进「模型标识」**：

```
可用模型（点一下填入）：deepseek-chat、deepseek-reasoner
```

填的名字不在列表里，测试结果直接说「所填模型不在上游列表里」。

## 三、顺带修了一个会让你白跑一趟的坑

你提到「两个槽位都可以配置云端 API」——这句话让我去查了发往云端的请求体，发现一个隐患：

`chat_template_kwargs` 是**本地服务专有**的参数，严格的云端 API（OpenAI、Azure）会因为不认识的参数直接 400：

```
Unrecognized request argument supplied: chat_template_kwargs
```

也就是说，槽位填云端 API 时可能**每个请求都先吃一个 400**。

现在的处理：撞上这种 400 就**摘掉这个参数重发一次**，并记住这个端点不认，以后不再带。本地服务该收的参数照收（实测本地路径不受影响）。

不是「预先不发」而是「撞了再摘」，因为本地服务需要这个参数，预先判断「这是不是本地」会误伤那些用域名指到内网的部署。
