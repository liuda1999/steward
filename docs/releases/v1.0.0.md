# steward v1.0.0

**本地模型管家。** 一个 OpenAI 兼容端点，两个平等的模型槽位：日常请求走基础模型，难题由模型自己判断后申请、并经网关核准才花钱问进阶模型。所有护栏都在网关侧，不在提示词里靠自觉。

首个正式版本。功能边界、错误分类和实测数据都已跑过真机，可以拿去做日常入口。

---

## 它解决什么

本地模型做长任务时会撞上三件事：窗口装不下、不知道什么时候该花钱、反复重试已经否决过的方案。steward 的做法是**在模型和上游之间插一层**，把这三件事变成可测量、可拦截的：

| 问题 | 做法 | 实测 |
|---|---|---|
| 窗口装不下 | 探真实窗口 → `/tokenize` 精确计数 → 六级裁剪 → 任务骨架 | 157,894 → 9,980 tokens（截 94%，仍能连贯作答） |
| 不知道何时该花钱 | 四条客观可判据 + 质量闸，不合格的委托单不计数、不花钱 | 9 类委托单形态对照，旧逻辑 0 拦截全放行 |
| 重复踩已否决的坑 | 任务骨架把「目标 / 约束 / 事实 / 已否决 / 当前位置 / 下一步」压成六行 | 真机 7–13 秒、148–290 tokens |
| 上下文被工具输出撑爆 | 交付物与工具输出落盘，回灌摘要 + 行锚点指针 | 一次裁剪 113 个文件 → 2 个，体积不变 |

## 这一版的内容

### 委托时机：不看"复杂"，看四个能回答的问题

原先写的是「只有任务确实复杂、且本地尝试后仍拿不准时才用」——「复杂」是主观词，模型没法据此决策。现在换成它真能回答的四条：前提够不够、能不能当场写出带失败判据的步骤、**代价是否不可逆**（这条硬性）、是否已经实际试过并失败。

再加一道质量闸：`ask` 为空或超长、`goal` 缺失、`diagnosis`/`review` 的 `tried` 为 none，直接退回让模型补充，**不消耗额度**。退回限两次，避免原地打转。

### 上下文治理：裁剪必须发生在工具循环内部

只在请求入口判一次预算是不够的——交付物和工具结果是在**循环中途**长大的，第 4 轮顶上来的三万字，入口那次判断根本看不见。现在每一轮发请求前都过一遍。

六级裁剪，前四级是纯字符串操作：

```
1 历史思维链 → 2 图片 → 3 工具输出摘要（全文落盘）→ 4 合并同类结果
  → 5 整对丢弃 tool_call + tool 结果 → 6 硬截断（仅在溢出自愈时）
```

裁剪完往 system 里塞一句 `[网关]` 标记。不标记的话模型会对着断裂的上下文编——它不知道自己少看了一段。

### 任务骨架：压完还得记得住

丢弃区超过阈值时，用本地模型把那段压成六行接回 system：`goal / constraints / facts / rejected / current / next`。四条约束写死不用提示词：

- `goal` 强制取用户原话（模型会把"最近在干什么"当目标）
- 一个请求最多建一次（多轮裁剪丢的是同一段历史）
- 区域头尾各取，尾部先占 60%（只取开头的话，`current` 会停在几百条消息之前）
- 独立连接池（共用会让 404 自愈连带关掉主请求的连接，实测 502）

模型不按格式输出、超时、返回聊天时退回机械骨架，**绝不阻塞主请求**。

### 存档与回收

统一 YAML 抬头（`kind/turn/created/chars`），路径只到「日期/类型/hash」，轮次只进抬头。一次裁剪的所有工具输出合并成一个文件，指针带 `#L120-340` 行锚点。

回收按 `max_age_days` + `max_total_mb` 取先到者，`clean_interval_s` 节流。**按目录名里的日期判断，不按 mtime**——mtime 是"最后一次写入"，一个天天追加的旧目录会永远显得很新、永远删不掉。

### 配额：四道闸，只拦进阶槽位

单请求次数 / 每日总量 / 工具轮次 / 最小间隔。计数在**放行时**就 +1，不等返回，避免并发绕过；连接失败、上游 4xx 自动退回。写盘持久化，重启不清零。

### refs：唯一会主动往外发的通道

默认关闭。开启必须显式配白名单（`enabled: true` + 空 `roots` 直接拒绝启动），路径做 `realpath` 解析防符号链接逃逸，黑名单挡 `.env` / `*.pem` / `.ssh`，每次展开都记审计。

### 两个槽位，可以只填一个

只有本地模型是最常见的用法，所以**空槽位是合法配置**：不注入 `consult_cloud`，每轮省下约 500 tokens 的工具定义。基础槽位缺失才拒绝启动（没有它一个模型都没有）。

### 端口

默认 **27418**：避开 80/8080 这类几乎总被占的端口，不用连续数字，落在 1024–49151 之间。撞端口会先自己试绑一次，报出占用的 PID，而不是丢一句 `WinError 10048`。

## 安装

```bash
git clone https://github.com/liuda1999/steward.git
cd steward
pip install -r requirements.txt        # Python 3.11+

python -m steward init                 # 配两个槽位，签发首把 key
python -m steward serve                # 默认 127.0.0.1:27418
```

客户端：

```python
base_url = "http://127.0.0.1:27418/v1"
api_key  = "st-..."                    # init 时打印一次，之后只存 hash
model    = "auto"
```

自检：

```bash
python -m steward --version
python -m steward test                 # 两个槽位连通性
python -m steward ctx                  # 真实窗口 / 预算 / 计数方式
python -m steward serve --check -c config.yaml
```

## 体积与开销

| 项 | 数值 |
|---|---|
| 代码 | 5,824 行 Python（14 个模块，含注释与空行） |
| 测试 | **342 个**，全绿 |
| 每轮固定注入 | **531 tokens**（system 21 + 配额 12 + 工具定义 498） |
| 运行时依赖 | `fastapi` / `uvicorn` / `httpx` / `pyyaml` |

每轮注入有硬上限断言守着（`total <= 560`、工具描述 `<= 240`），提示词可以改，但不能悄悄长回去。

测试里有两类值得单独提：

- `tests/test_audit.py`：把**修复前的实现原样搬进来做对照组**，同一份数据跑两遍看差异。另外做了三次回归注入（改坏代码），确认审计真的会报警。
- `tests/test_reliability.py`：并发抢额度、畸形上游响应、异常路径退还配额。

## 已知限制

- **单进程假定。** `state/usage.json` 用文件锁保护，两个网关指向同一个文件会互相覆盖计数。
- **Windows 上 `chmod 0600` 是空操作**，`keys.json` 走默认 ACL。它只存 hash，拿到文件也拿不到 key。
- **骨架是摘要，不是备份。** 丢掉的报错原文、代码片段不会回来——但那些多半已经落盘，模型能读回来。真正的风险是它编造缺失部分，所以骨架末尾固定写了一句「缺细节时用工具重新确认」。
- **有代理的环境里 `git push` 可能过不去**，用 `python scripts/publish.py` 代替（自动找可用 CA，走不通退回 Git Data API）。

## 名字的来历

这个项目有两代前身，都不是现在这个东西：

1. **接第三方 MCP**（`cli-bridge-mcp`），工具叫 `ask_mycloud` / `ask_cascade`。问题是护栏只能数次数，判断不了「这活该不该上云」。
2. **自建网关**，叫 `cloudbridge`——名字只说了「连着云端」，但它实际做的是预算、窗口、存档三件管家活。

`steward` 取的是「打理」：管账、管窗、管档案、管外发。前两代的文档留在 `legacy/`，`HANDOFF-PROTOCOL.md` 里的委托单格式与四段式交付物定义仍在用。
