# steward v1.6.3

**首次启动不该探上游窗口。** 槽位还是模板里的 `your-base-model` 时，探测注定失败，只会在日志里留一句「没能探到上游真实窗口，按 32768 保守估计」——读者以为是报错。正确的顺序是：起服务 → 进控制台填上游和 key → 保存并重启 → 这时才探。

补丁发布，不改配置、不改协议。

---

## 一、问题：探测跑在了配置前面

`server.py` 的启动流程里，探测是**无条件**执行的：

```python
limits = await refresh_limits()          # 一启动就探上游
if limits.source in ("default", "config"):
    logger.warning("没能探到上游真实窗口，按 %s 保守估计…")
```

首次启动时 `base.model` 还是 `your-base-model`、`base_url` 指向模板里的默认地址。这次探测探的是一个不存在的模型，必然失败，于是：

- 白等一次 3–6 秒的连接超时
- 在「配置校验通过 OK」之后，突然来一句看起来像故障的告警
- 用户还没进过控制台，根本没有机会填上游

同一段日志里还混着一条 `steward.server` 的 INFO 从不出现的问题——查下来是 `start` 入口**从来没调用过 `logging.basicConfig`**（只有 `serve` 调了），root logger 停在 WARNING，说明性日志全被吞掉，只剩告警。这也是为什么「上下文：窗口 …」一直不显示。

## 二、修复

### 2.1 探测前先看槽位配没配

`AppCfg.base_ready()`：`base_url`、`model` 都非空，且 `model` 不是模板占位值，才算「配好了」。

- **没配好**：完全跳过探测，不发任何请求，只记一条 INFO：
  `基础模型还没配（base.model 是模板占位值）：跳过窗口探测。在控制台填好槽位并点「保存并重启」后会自动探测。`
- **配好了**：照常探测。探不到时，告警改成可操作的说法：
  `上游没返回窗口大小，先按 32768 估计。配好模型或上游恢复后重启会自动重探；也可以写 context.ctx_limit 固定它。`

### 2.2 `start` 入口补上日志配置

抽出 `_configure_logging()`，`start` 和 `serve` 共用；`_serve_loop` 每轮重启都重配（`log_level` 可能被改过）。`basicConfig` 在 root 已有 handler 时是空操作，所以额外显式 `setLevel` 一次。

效果：`上下文：窗口 131072 tokens（每槽 … / 来源 props）` 这类说明性日志终于看得见了。

### 2.3 横幅不再甩绝对路径

`key`、`config.yaml`、`console.token` 改成**相对当前目录**显示（`start` 会先 cd 到项目根）。配置在项目外（`--config /abs/elsewhere`）时自动回退绝对路径，不会藏住文件位置。

## 三、验证

| 场景 | 结果 |
|---|---|
| 首次启动（占位配置） | **0 秒起服务**，0 个探测请求，日志明确写「跳过窗口探测」，无任何告警 |
| 已配置 + 上游可达（真机 llama.cpp） | `窗口 131072 / 来源 props`，`/tokenize` 可用，精确计数 |
| 已配置 + 上游不可达 | `窗口 32768 / 来源 default` + 可操作告警，服务照常可用 |
| 相对路径 | `config.yaml`、`state\keys.json`、`state\console.token` |
| 全量测试 | **483 通过 / 1 跳过** |

新增 `tests/test_startup_probe.py`：

- 占位模型时**一个探测请求都不发**（用记录型 transport 断言 `/props`、`/models`、`/tokenize` 均未出现）
- 真实模型名时会探测，且失败时给出「先按估计值跑」的说明
- 横幅路径在项目内是相对路径

## 四、升级

- 直接替换代码，无需改 `config.yaml`
- 首次启动会明显变快（不再等探测超时），日志也会多出几行 INFO —— 那是本来就该显示的说明
- 如果你更喜欢安静，把 `server.log_level` 改成 `warning` 即可
