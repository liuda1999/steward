# steward v1.5.0

**补上部署与启动的文档，给本地一个真正的入口，顺便修掉一个 `--port` 从来没生效过的老 bug。**

起因是一句话：「关于项目的部署与启动，在 GitHub 的项目文档中没有明确的写出，本地实际使用时也缺少一个正式启动项目的入口。」

查下来发现，问题比"文档没写"要严重一点：**README 里写的启动流程，在全新克隆下是直接失败的。**

---

## 一、发现的问题

### 1.1 `python -m steward serve` 在全新克隆下起不来

```
$ git clone https://github.com/liuda1999/steward.git
$ cd steward
$ python -m steward serve
[配置] 错误  base.base_url 未配置（基础模型）
[配置] 错误  base.model 未配置（基础模型）
[配置] 以上必须修掉才能启动：基础模型缺失时网关没有任何可用模型。
```

原因是 `find_config()` 只在**当前目录**找 `config.yaml`，而随包的示例配置在
`steward/config.yaml` 里 —— 包内，不是工作目录。于是配置找不到，校验不过，
进程退出。

README 里写的是「启动（先用随包示例配置）」，但代码从来没实现过这句。

新用户拿到这份代码，面对的是：不知道要建配置文件、不知道建在哪、不知道
叫什么名字、不知道填什么。**这不是"用户不会"，是文档没写清楚。**

### 1.2 项目装不上

没有 `pyproject.toml`，`pip install -e .` 直接报错：

```
ERROR: file:///... does not appear to be a Python project:
neither 'setup.py' nor 'pyproject.toml' found.
```

所以"正式的启动入口"这个词，在 v1.4.0 之前是不存在的 —— 只能手敲
`python -m steward serve`，而且还得先 cd 到正确的目录。

### 1.3 `--port` 从来没生效过（真 bug）

README 里写着「临时换端口不用改配置：`python -m steward serve --port 27xxx`」。

实际上**这个 flag 一直是被忽略的**。

原因在 `serve` 的循环里：为了支持控制台「保存并重启」，每一轮都会
**重新读一遍配置**：

```python
cfg = load_config(cfg_path)          # ← 重新读，覆盖被冲掉
host, port = cfg.server.host, cfg.server.port
```

而命令行覆盖只在上层盖了一次。于是 `--port 27xxx` 悄悄用了配置文件里的
27418 —— **用户以为自己换了端口，实际没换**。

撞上端口冲突时更是完全摸不着头脑：终端会说「27418 被占用」，而用户明明
指定了另一个端口。

修法是把覆盖挪到重新读配置**之后**（每轮都盖）：

```python
cfg = load_config(cfg_path)
if getattr(args, "host", None):
    cfg.server.host = args.host
if getattr(args, "port", None):
    cfg.server.port = args.port
```

## 二、现在是什么样

### 2.1 一条命令

```bash
git clone https://github.com/liuda1999/steward.git
cd steward
./scripts/start.sh          # Windows: scripts/start.bat
```

```
  steward 1.5.0  启动检查

  [1/4] Python 3.13.14  OK
  [2/4] 依赖齐全  OK
  [3/4] 首次启动，已生成配置：/path/to/steward/config.yaml
  [4/4] 配置校验通过  OK
```

`start` 把整条首次启动链路收进一条命令：**检查环境 → 装依赖 → 生成配置 →
起服务**。跑不通时给出具体到命令的下一步，而不是一句「配置错误」。

对应的新子命令：

```bash
python -m steward start          # 正式启动入口
python -m steward start --check  # 只做启动前检查，不起服务
```

### 2.2 首次启动自动生成配置

找不到配置时，用随包模板生成一份当前目录下的 `config.yaml`：

- 模板在**包内**（`steward/config.example.yaml`），`pip install` 之后照样找得到；
- 生成的是**副本**，不往包目录里写（site-packages 只读是常态，写进去是安装事故）；
- 已经有配置时**绝不覆盖** —— 那是用户的数据。

配套的 `init` 也调整了：一份原封不动的模板不算「已有配置」，可以直接覆盖。
不这么判的话，「先 serve 生成配置，再 init 配一遍」这条常见路线会被一句
「已存在，要覆盖加 --force」堵住，而 `--force` 看起来像危险操作。

### 2.3 模板里进阶槽位留空

原来模板里进阶槽位填的是 `https://your-provider.example.com/v1` —— 一个
假域名。这会让网关认为「云端可用」，于是注入 `consult_cloud` 工具，每轮
都往一个不存在的域名发请求。

空槽位才是合法且更省的状态：不注入工具，每轮省约 500 tokens。

启动时如果 `base.model` 还是模板占位值（`your-base-model`），会明确提示
「打开控制台填上真实的模型标识，否则每次请求都会失败」—— 比让请求去打
一个不存在的模型、拿一个看不懂的 404 强。

### 2.4 能装成命令了

```bash
pip install -e .
steward serve
```

发行名在 PyPI 上叫 `steward-gateway`（`steward` 这个名字被别人占了），
但**命令行入口仍然叫 `steward`**。

`pyproject.toml` 里的依赖清单和 `requirements.txt` 由测试盯着同步 ——
两份漂移的话，会出现「照 README 装能跑，pip 装不能跑」这种最难查的问题。

## 四、测试

新增 `tests/test_deploy.py`，**31 个用例**，盯的是「入口通不通」而不是
「功能对不对」：

- 打包元数据：版本号一致、入口函数可调用、依赖清单不漂移、包数据带上了控制台页面；
- 配置定位：模板随包、模板进阶槽位为空、首次启动能生成配置、已有配置不被覆盖、
  不往包目录里写、模板与用户配置的区分；
- 命令行：`start` 存在且注册、四步检查都报、`--check` 不起服务；
- 启动脚本：两个平台都在、git 索引里是可执行位（100755）、`.bat` 全 ASCII
  （cmd.exe 按控制台代码页读，非 ASCII 会变乱码）、README 里提到了；
- 部署文档：存在、覆盖了哪些主题、端口和代码一致、引用的命令都真的存在；
- **回归**：`--port` / `--host` 覆盖不会被重读配置冲掉（还原修复即变红）。

全量 **452 个用例通过**，1 个跳过（Linux 专用的启动脚本端到端测试）。

## 五、升级注意

- `config.yaml` 不在版本控制里，`git pull` 不会动它；
- 新版本的配置项默认值**不会自动写进**你的旧文件 —— 有意如此，否则一次
  `git pull` 就能改掉你手改过的配置。启动日志的 `[配置] 注意` 会告诉你哪些要手动补；
- 存量交付物存档（`.steward/artifacts/`）不受影响。
