# steward v1.6.9

**给「求助通道」补上四个确定缺陷，并用 192.168.0.108 上的真实大模型跑了一遍验收审计。**

补丁发布：不改变「模型自决 + 网关硬拦」的取向，不加错误计数、不加卡住提示、不给收尾额外机会。

---

## 一、修了什么

| 缺陷 | 修法 |
|---|---|
| 连接失败后 `refund()` 退了额度，但 30 秒冷却仍挡着，想问也问不出去 | 冷却改由 `mark_called()` 在**真拿到交付物后**才启动；退款路径根本不产生冷却 |
| 客户端自带同名 `consult_cloud`、或用 `tool_choice` 锁死别的函数时，只在服务端写一条 WARNING，调用方只看到「模型一直不问」 | 新增 `X-Steward-Consult` 响应头与 `x_steward.consult` 字段，给出 `available` / `advanced-slot-empty` / `client-tool-name-conflict` / `tool-choice-locked` |
| 轮次用尽时的收尾文案写「进阶模型咨询轮次已用尽」 | 改成「本轮工具循环已达上限」——`max_tool_rounds` 计的是总轮次，`precheck` 退回和配额拒绝也算一轮，可能一次都没真问过 |
| `guard.refund()` 的注释没说清冷却归属 | 明确「只退计数，不动别的请求留下的合法冷却」 |

第 1 项与「冷却仅成功后计时」是同一处改动，没有在 `refund()` 里硬撤时间戳：那样会误撤别的请求刚建立的成功冷却。新增三条 `tests/test_guard.py` 用例锁住「放行不启动冷却」「成功后才拦」「退款后立刻能再问」，另有五条 `tests/test_e2e.py` 用例覆盖四种通道状态与文案。

## 三、验收里发现的一件事（不是代码缺陷）

当前 `config.yaml` 用的是 **`protocol: responses` + `thinking: auto`**。在这台上游上，这组参数会真实复现此前担心的尴尬：

- 强制 `tool_choice` 指向 `consult_cloud` 时，模型没吐出 tool_call（HTTP 200 但 `cloud_calls=0`）；
- 第二次生成了**未闭合引号**的委托单参数，上游 router 返回 500 `Failed to parse tool call arguments as JSON: ... missing closing quote`，网关按要求透传 502；
- 启动日志里 `/tokenize` 返回 400，精确 token 计数退回字符估算。

换成 `protocol: chat` + `thinking: off`（模板与文档一直推荐的组合）后，同一组 9 项检查全绿。根因是推理型模型的思维链吃掉生成预算、叠加上游 responses 协议对工具参数更敏感的解析，属于**部署参数与上游实现的组合问题**，不是本次改动引入的。

**建议**：把 `base.thinking` / `advanced.thinking` 设为 `off`，或把两个槽位切回 `chat` 协议。否则「想求助却发不出去、模型反复死磕」会在这套配置下真实发生。另外当前两个槽位指向同一个本地模型，求助等于问自己——要真正有外援还得把 `advanced` 指向另一个端点。
