**对 v1.6.1–v1.6.5 这一串修复做了一次完整审计，发现两个问题：重新签发的顺序会在失败时把设备锁在门外；控制台把上游返回的模型名直接拼进 `innerHTML`。**

## 二、发现并修复的两个问题

### 2.1 重新签发：先吊销、后签发

原来的顺序是：

```js
await api("keys/revoke", { id: old });     // 先把旧的干掉
const d = await api("keys/new", ...);      // 再签新的
```

签发这一步只要失败（网络抖动、`keys.json` 写不进去、进程刚好在重启），那台设备就**既没有旧 key 也没有新 key**，直接失去访问权。

现在反过来：**先签发、后吊销**。最坏情况是两把 key 同时有效，用户手动吊销旧的即可——比把人锁在门外好。加了 `try/catch`，失败时把错误显示在签发框里，不再静默。

### 2.2 上游模型名未转义就进 `innerHTML`

模型列表是这么拼的：

```js
d.models.map(m => `<a href="#" data-pick="${m}">${m}</a>`)
```

`m` 来自上游的 `/v1/models`，不是我们自己写的。一个引号就能截断 `data-pick` 属性，一个 `<img onerror=…>` 就能注入脚本。控制台持有口令、能签发 key、能改配置，这类注入的后果不止是页面难看。

加了 `esc()`，对 `& < > " '` 做实体转义，用在：

- 上游模型名（文本与属性）
- key 的标签与 id（标签来自用户输入，同样可能带引号）
